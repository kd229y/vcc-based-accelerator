# SoC 軟體功能模型與完整驗證系統建置規畫書

版本 1.0　日期 2026 年 11 月 3 日

後續實作進度與實測結果已另存於 [執行與結果說明](README_執行與結果.md)。本文件保留實作前規畫與當時進度；目前狀態以執行報告為準。

本規畫以原本 Morton code 整體 SoC 方案為對象，安排從現有資料包到完整軟體功能模型、自動驗證、效能與能量評估的實作流程。目標是讓同一筆點雲、機器人模型與起終點輸入後，可以追蹤各模組的結果，獨立檢查最終路徑，並輸出可重現的驗證報告。

執行順序為先固定介面與數值規格，建立最小參考計算及自動比對框架，再逐個實作與驗證模組。完整 SoC 模型與完整驗證系統在這個過程中一起形成。功能正確性通過後，才加入時間、記憶體與能量模型。

## 1 目標範圍與目前進度

### 1.1 最終要完成的系統

建構引擎負責點雲剔除、量化、Morton 編碼、中心點濾波及排序建表。環境記憶體保存點資料、格目錄、AABB 與版本。規劃引擎包含取樣、最近鄰、Extend 與 Connect、運動邊驗證、定點 FK、環境及自碰撞檢查、RRT 樹更新及路徑回溯。

最終功能模型必須執行上述完整流程。中間階段可以借用浮點 VAMP 的規劃或 FK 來隔離問題，但應標示哪些模組仍由參考軟體提供，避免將部分卸載結果當作整顆整數 SoC 的結果。

第一個入口使用已保存的 XYZ 點雲。若最終硬體採深度影像輸入，需再加入深度反投影與座標轉換，以及對應的影像、相機內外參與參考點雲；完成 XYZ 入口不能代表這些模組已通過。

## 2 輸入輸出與驗證邊界

### 2.1 測試輸入

每筆 case 由點雲、Panda 模型版本、起始及目標關節角度、設計設定與取樣序列組成。統一使用公尺與弧度，並記錄關節順序、世界座標系、手指開度及自碰撞配對規則。

同一個測試需保存輸入校驗碼、軟體版本及設定校驗碼。進行不同方案比較時，不重新隨機產生另一份點雲；規劃取樣與點雲表面取樣是兩種不同隨機來源，應分別保存。

### 2.2 系統輸出

| 輸出 | 必要內容 |
|---|---|
| 規劃狀態 | 成功 輸入無效 容量不足 預算用完 內部錯誤等明確分類 |
| 路徑 | 依序排列的七維關節角度 起終點及組態點數 |
| 識別資訊 | request ID 環境版本 case ID 設定與模型版本 |
| 中間結果 | 濾波點 格目錄 FK 球 查詢結果及 RRT 事件 |
| 驗證報告 | 各測試是否通過 第一個差異及重現方式 |

RRT 在有限迭代內未找到路徑，回報預算用完；不能據此宣稱問題已被證明無解。輸出的幾何路徑也不自動包含速度、加速度、時間參數化或馬達控制命令。

### 2.3 正確性分為四個層次

數值正確性檢查整數運算是否符合位元與捨入規格。幾何正確性檢查 FK、碰撞與保守誤差處理。演算法正確性檢查最近鄰、運動邊與 RRT 狀態。整合正確性檢查資料、記憶體版本與模組間完成條件。

四個層次分別驗收。速度快、能找到路徑或動畫看起來正常，均不能取代正確性檢查。

## 3 軟體架構與參考計算

### 3.1 建議分工

以 C++ 建立接近硬體數值規格的功能模型；以 Python 管理案例、輸入輸出、統計與報告。獨立參考計算可先使用 Python 或簡單的循序 C++，以可理解、可檢查為優先。第一階段不要求 cycle accurate 模擬，也不需要先建立完整作業系統或處理器模擬。

所有模組應先有可直接呼叫的函式介面及序列化輸出。功能模型不依賴視覺化介面才能運作，視覺化只作為偵錯輔助。

### 3.2 三種程式的角色

| 程式 | 功能 | 比較原則 |
|---|---|---|
| 高精度數學與幾何參考 | 獨立 FK 暴力碰撞與距離計算 | 檢查誤差與幾何結果 |
| 簡單整數規格參考 | 明確處理位元 捨入 溢位及平手 | 與待測模型逐 bit 或逐事件比對 |
| SoC 功能模型 | 模擬建構 規劃及模組協作 | 接受相同測試輸入並輸出中間結果 |

原始 VCC 與 VAMP 作為應用及效能 baseline。它們可能有版本問題，不能成為唯一的正確性標準。參考計算應避免共用待測的 Morton 索引、AABB 剔除與 FK 最佳化程式，以免同一個錯誤同時出現在兩邊。

整數模型與浮點 VAMP 可能因量化、保守碰撞判定或平手規則而產生不同的樹與路徑。只有在數值規格、取樣序列及仲裁順序一致時，才要求逐步完全相同；其餘情況分別檢查規格符合性與路徑品質。

### 3.3 建議新增的目錄

下列目錄尚待建立。現有 upstream、data 及 examples 保持可追溯。

```text
spec/                 介面 數值規格 誤差界與變更紀錄
reference/            獨立參考計算與簡單整數版本
soc_model/            C++ 功能模型及模組介面
tests/unit/           模組測試
tests/integration/    模組串接與記憶體版本測試
tests/system/         點雲到路徑的完整案例
runner/               案例執行 差異定位及報告工具
simulation/           後續 cycles 記憶體與能量模型
runs/<run_id>/        每次執行的輸入摘要 結果 trace 與報告
```

## 4 階段與里程碑

### P0 固定最小規格與執行基準

先選 Panda，使用現有 box、bookshelf_thin 與 cage 範例確認輸入格式。完整 MBM 資料再由可執行的 VAMP baseline 檢查起終點；現有三筆範例沒有這個檢查結果，不預設一定有效。

完成 input 與 output schema、各模組介面、數值規格、錯誤狀態及環境更新規則。位元數與網格尺寸可先依 HackMD 提出候選值，但要明確標示假設，不把 500 MHz 或記憶體延遲當成已達成的硬體條件。

交付物為 spec 文件、固定測試清單、可重現 baseline 命令、環境版本與一份 baseline 結果。驗收時應能在相同軟體與輸入下重現結果，並清楚區分有效問題、輸入無效、timeout 與容量不足。

### P1 建立最小驗證框架與獨立參考

建立 runner，能讀入一個 case，呼叫參考與待測模組，比較結果，並將差異輸出到固定目錄。先用簡單案例驗證框架本身，例如單點、空資料、已知 Morton key 與已知距離結果。

每個測試保存輸入、預期輸出、實際輸出及比較規則。以刻意放入的錯誤確認 runner 真的會失敗，例如改錯一個 key、移除一個點或提前回報完成。

交付物為 reference 初版、runner、測試分類及機器可讀報告。驗收要求是正確案例通過、故障案例被抓出，而且失敗可由單一 case 與設定重現。整顆 SoC 不必在此時完成。

### P2 完成環境建構與碰撞查詢

依序實作剔除與量化、Morton 編碼、中心點濾波、壓縮、排序或分桶、粗格目錄與 AABB，最後加入球對環境的查詢。依實際選定方案保存 hash、offset、point pool 與 padding 的內容，不混用不同建表方案的記憶體格式。

參考濾波以簡單 map 分格並挑選代表點；參考排序使用標準排序；參考碰撞對保存點雲逐點計算，完全不使用待測格目錄。三者分別定位挑點、資料排列及查詢錯誤。

交付物包含建構與查詢模組、環境記憶體快照、各階段輸出及差異報告。驗收要求是同規格逐項一致，沒有靜默丟點或 padding 誤判，容量不足有明確狀態，且大半徑與邊界查詢均通過。

先驗證對保存點雲的查詢正確性，再驗證對原始點雲的濾波與量化覆蓋。這兩種結果分開報告；對較少點正確不等於對原始障礙完整。

### P3 完成 FK 自碰撞與運動邊驗證

先從同版本 URDF、SRDF 與手指設定建立獨立高精度 FK，核對球的 link、局部位置、半徑及自碰撞配對。再建立整數規格參考及定點 FK，處理查表、乘加中間精度及捨入。

對隨機合法組態、關節上下界與幾何臨界組態，比較每顆球的中心誤差。量測最大誤差並推導適用輸入範圍的誤差上界；環境球碰撞與機器人自碰撞所需的放大量分別計算。涉及兩個有誤差的球心時，不能只計入單邊誤差。

接著實作運動邊內插與碰撞驗證，測試零長度邊、短邊、長邊，以及兩端合法但中間碰撞的情況。若採離散檢查，要明確定義步長及保證範圍；高密度抽樣結果不宣稱為連續碰撞證明。

交付物為 FK 比對資料、誤差分析、自碰撞測試與邊驗證測試。驗收要求是整數規格比對通過，誤差未超出規格，且未以過小半徑或過疏檢查步長換取速度。

### P4 完成最近鄰與 RRT 狀態機

最近鄰先採全節點掃描作為正確參考，固定關節距離與平手規則；若之後採更快索引，仍保留掃描版作比較。取樣端保存完整組態序列，避免只靠 seed 而忽略不同 RNG 或呼叫次數造成的差異。

依序加入取樣、最近鄰、Extend、Connect、插入節點、parent 更新、雙樹交換及路徑回溯。每個階段記錄事件，並在第一個不符合規格的位置停止比對。零距離、重複節點、樹滿、起終點相同及預算耗盡需有明確處理。

交付物為循序規格參考、整數 RRT 模型及事件 trace。驗收要求是同規格循序執行可重現；parent 合法且不形成環；只有已通過規定邊驗證的節點可以插入；回溯順序確實從起點到目標。

### P5 串接 SoC 並驗證資料流

將建構、環境記憶體、FK、查詢與 RRT 串成一個執行入口。先以單一環境版本及循序請求完成流程，再加入雙緩衝、多筆在途查詢、取消與 backpressure 等設計中的並行行為。

以事件佇列加入可變回覆延遲，不必先精確描述每一個 clock。固定仲裁規則；若允許不同排程導致不同合法路徑，驗證狀態與幾何性質，不強制所有排程逐事件相同。

交付物為完整功能模型入口、模組間事件紀錄與整合測試。驗收要求是請求不遺失、結果不重複或配錯 ID、環境版本符合規格、被使用的 buffer 不被覆寫，且不因延遲或回覆順序改變而提早回報無碰撞。

### P6 建立獨立路徑總驗證與回歸測試

完整輸入經 SoC 模型後，將成功路徑交給獨立驗證器。它以高精度 FK 及獨立幾何檢查，確認端點、關節限制、自碰撞及全部運動邊。先對相同保存點雲驗證，再對原始場景幾何做應用層驗證，分別標示結果。

先用手工小案例與選定有效場景定位問題，再擴大到全部 700 組。保留原始無效問題的數量與原因；不能只留下成功案例統計。對新的隨機測試，固定並保存 seed 與完整生成參數。

交付物為總驗證器、回歸清單、逐案例結果及可重現故障包。驗收要求是所有必要正確性測試通過，所有回報成功的路徑通過已定義的獨立檢查，且沒有尚未處理的漏判、靜默溢位或資料流錯誤。

### P7 加入效能與記憶體模型

在已通過功能驗證的模型上加入每個單元的操作數與 cycles 註記，模擬引擎數量、SRAM bank、佇列、DMA、頻寬及外部記憶體延遲。RRT 繼續依實際碰撞結果前進，以 functional first 方式產生後續工作。

先以簡單人工案例檢查 cycles、交易數與資料量是否可手算，再使用完整工作負載。雙緩衝或計算搬移重疊時，端到端時間取事件關鍵路徑，不能把所有單元時間直接相加。

交付物為可設定的事件模型、存取 trace、模組使用率與效能報告。驗收要求是時間模型不改變規定的功能結果，且每個延遲、頻寬及時脈假設都有來源或明確標記為參數掃描。

### P8 加入能量估算與硬體設計比較

分別計數整數運算、SRAM 讀寫、外部記憶體交易及執行期間的靜態能量。每個能量係數需註明器件資料、工具估算、製程條件或合成結果；沒有係數時只報操作數及流量。

先比較同品質條件下的每次規劃能量，再在相同吞吐量或延遲目標下比較功率與資源。成功與失敗案例的能量分開呈現，並另外報告整批請求的總能量及完成有效路徑的數量。

交付物為能量模型、參數來源表與設計比較。驗收要求是不把 CPU 測得的速度當作 SoC 時間，也不把未校正的操作數模型寫成實測功耗。面積與可達時脈仍需後續 RTL 合成確認。

### P9 匯出 RTL 驗證材料

軟體階段通過後，凍結數值規格與資料布局，匯出二進位輸入、預期輸出、SRAM 快照、query 與 RRT 事件，供後續 RTL testbench 使用。記錄端序、packing、對齊與有效資料長度。

RTL 的位元結果與功能模型逐項比較，cycles 再與效能模型比對並校正。此階段是後續硬體工作的銜接，不列為第一個軟體模型完成的必要條件。

## 5 模組驗證矩陣

| 模組 | 主要輸出 | 必測情況 | 主要驗收 |
|---|---|---|---|
| 剔除及量化 | 有效標記 整數座標 | 負值 格面 上下界 非有限輸入 | 索引及捨入符合規格 |
| Morton 編碼 | fine key coarse key | 已知向量 最大座標 階層關係 | 逐 bit 一致 |
| 中心點濾波 | 代表點與距離 | 重複點 平手 輸入重排 hash 碰撞 | 固定輸入下挑點正確 容量不靜默失敗 |
| 排序與建表 | 排序點 目錄 AABB | 空格 全空 單格滿 padding | 點不遺失不重複 目錄與界限正確 |
| 環境碰撞 | 碰撞結果 | 相切 大半徑 邊界 空資料 | 同規格對暴力參考一致 |
| 定點 FK | 球心 半徑 | 關節極值 多層連乘 | bit 規格正確 幾何誤差受控 |
| 自碰撞 | 組態有效性 | 允許配對 臨界接觸 | 配對規則與保守誤差正確 |
| 最近鄰 | 節點 ID 距離 | 平手 重複節點 空樹 容量上限 | 對全掃描參考一致 |
| 邊驗證 | 邊有效性 | 端點合法但中間碰撞 零長度 | 內插與檢查完整 |
| RRT 狀態機 | 樹 parent 路徑 | 雙樹交換 Connect 終止 樹滿 | 不插入未驗證邊 回溯合法 |
| 記憶體及控制 | 回覆 ID 版本 完成訊號 | 延遲 亂序 取消 雙緩衝 | 不漏單不配錯 不提早完成 |

濾波平手保留先出現點時，重新排列輸入可能改變代表點，不能一概要求輸入任意重排後結果完全相同。測試應分開檢查相同序列的可重現性與無平手資料的重排性質。

## 6 自動驗證報告與故障定位

### 6.1 每次執行保存什麼

每次 run 保存輸入路徑與 SHA 256、設定與來源 commit、執行命令、軟體環境、開始時間、模組測試結果、系統輸出與第一個差異。大型 trace 可只在失敗時完整保留，但摘要必須能定位回原始 case。

建議單筆結果包含 case ID、status、失敗階段、預期值、實際值、容差、碰撞參考結果、環境版本及重現命令。PASS 與功能失敗採明確退出碼；預算耗盡或初始輸入無效是系統狀態，不與測試框架崩潰混成同一類。

### 6.2 建議的總驗證入口

以下是後續實作介面提案，目前資料包沒有這支完整 runner。

```text
python runner/run_validation.py --suite smoke --config spec/design_v1.json
python runner/run_validation.py --suite modules --config spec/design_v1.json
python runner/run_validation.py --suite system --config spec/design_v1.json
python runner/run_validation.py --suite regression --config spec/design_v1.json
```

smoke 確認環境、輸入與單筆流程；modules 執行各模組比對；system 執行完整點雲到路徑及獨立路徑驗證；regression 執行固定資料集與故障案例。可先以單一語言完成 runner，實際命令在 P1 定稿。

### 6.3 首次完整執行的預期產物

```text
runs/<run_id>/
  run_manifest.json           輸入 設定 程式與環境版本
  module_results.json         各模組測試與差異
  environment_snapshot/       濾波點 格目錄 AABB 與有效長度
  planner_events.jsonl        取樣 NN 邊驗證 插入及 Connect 事件
  path.json                   status 及七維路徑
  path_validation.json        獨立驗證與適用保證範圍
  summary.csv                 各案例狀態與量測
  report.md                   可閱讀的結果說明
```

沒有成功路徑時，path 檔仍保存 status 與失敗原因，不能捏造中間路徑冒充解答。上述產物是在模型實作後才產生，不以現有輸入點雲代替。

## 7 判斷方案好不好的指標

### 7.1 正確性與品質

| 指標 | 定義與使用方式 |
|---|---|
| 必要測試通過率 | 固定必測案例全部通過才進下一階段 |
| 碰撞漏判 | 參考為碰撞 模型判無碰撞的案例數 必須定位並修正 |
| 額外碰撞判定 | 因保守誤差放大產生的額外阻擋 另報比例及分母 |
| FK 誤差 | 每球中心誤差的分布與測試最大值 另列推導上界 |
| 規劃成功率 | 有效問題在固定預算內輸出有效路徑的比例 |
| 路徑品質 | 關節空間路徑長度與適用距離定義 必要時另列 clearance |
| 容量與狀態錯誤 | 溢位 不合法位址 遺失請求 錯誤版本及死鎖 |

有限測試只能說在列出的測試與假設下通過。若要主張原始幾何的連續安全，必須另外完成覆蓋與誤差界分析；報告不把它與測試零漏判混為一談。

### 7.2 效能與硬體成本

| 指標 | 報告方式 |
|---|---|
| 端到端延遲 | 輸入可讀到有效路徑輸出 包含搬移及初始化 報 median 與 P95 |
| 建構與規劃分解 | 濾波 排序 建表 FK NN 查詢及控制等待 |
| 持續吞吐量 | 多次環境更新與規劃並行時 每秒完成有效請求數 |
| 峰值 SRAM | 含表格 點資料 padding 暫存 雙緩衝 RRT 樹與佇列 |
| 外部交易 | 實際模型交易次數及 bytes 區分讀寫及更新 |
| 運算與等待 | 距離計算 hash probe 使用率與等待 cycles |
| 每次規劃能量 | 區分成功與失敗 所有係數有來源 |
| 面積與功率 | 有合成或校正模型才報 先列面積相關資源量 |

性能比較使用同一批輸入與預算，同時報告品質與失敗；若只在共同成功案例比較延遲，另列完整集合的成功率與失敗成本。計時與詳細 trace 可分開執行，避免偵錯輸出影響量測。

### 7.3 比較組

A 為原始 VCC；B 保留原結構但使用相同目標網格；C 採相同網格的 Morton 浮點資料結構；D 為整數 SoC 模型。B 對 C 分析資料組織效果，C 對 D 分析整數化影響，A 對 D 分析應用整體效果。

CPU 執行時間與 SoC 模擬 cycles 分欄呈現。加速比的兩端必須使用相容的端到端範圍；不能將 CPU 全流程時間除以僅距離單元時間。環境重用次數另作掃描，分析每 frame 重建與靜態環境下建構成本如何攤提。

## 8 建議時程與階段驗收

下表為一位主要實作者投入開發的初步安排，依工具鏈、數值誤差分析與測試發現調整，不是固定交付承諾。若階段驗收失敗，先修正或重訂規格，不在已知錯誤上疊加效能結果。

| 時段 | 主要工作 | 可檢查的里程碑 |
|---|---|---|
| 第 1 週 | P0 及 P1 初版 | 規格初版 baseline 能跑 最小 runner 能抓故障 |
| 第 2 至 3 週 | P2 | 點雲建構與查詢 對獨立參考通過 |
| 第 4 至 5 週 | P3 | 定點 FK 自碰撞 邊驗證及誤差紀錄 |
| 第 6 至 7 週 | P4 | 完整取樣序列下 RRT 狀態與回溯正確 |
| 第 8 至 9 週 | P5 及 P6 | 點雲到路徑總驗證 整合與完整回歸報告 |
| 第 10 至 11 週 | P7 及 P8 | functional first 效能 記憶體及有依據的能量分析 |
| 後續硬體階段 | P9 | RTL 向量 逐 bit 比較及 cycles 校正 |

跨階段的原則是規格變更必須帶出新的設定版本與受影響測試。若改動捨入、格邊界或球半徑，需重跑建構、碰撞與路徑驗證；若只改 trace 格式，可限縮為格式與讀寫相容性檢查。

## 9 主要風險與處理方式

### 9.1 參考程式與待測程式共享錯誤

暴力碰撞不使用 Morton 剔除；FK 參考從模型描述獨立建立；已知解析小案例與刻意故障用來檢查驗證器。VCC 的 CAPT 已知版本問題與容量不足情況須另外監測，不能只要求新模型重現 baseline 的每個結果。

### 9.2 整數化與濾波造成幾何差異

將濾波覆蓋、點座標量化、FK 與距離運算誤差分開分析。對照浮點版時，把合理保守差異與真正漏判分開。若放大量讓窄縫成功率下降，報告這個代價並重新評估精度，而不是移除必要誤差保護。

### 9.3 模型太早加入大量硬體細節

先讓循序功能流程可比對，再加入並行事件，最後校正 cycles。記憶體模型與功能模組維持明確介面，使延遲設定改變時能重用相同的功能驗證。

### 9.4 資料格式與場景條件不一致

保存原始 JSON 與校驗碼，明確區分來源編號與陣列索引、公尺與毫米、弧度與正規化組態。URDF、SRDF、產生的 FK 及手指設定一致，才能使用同一組起終點與自碰撞規則。

### 9.5 深度影像入口資料尚未準備

若最終保留深度影像入口，新增相機內外參、深度單位、無效值規則、像素順序與反投影參考。可先由已知場景產生可驗算的合成深度案例，再加入真實影像。幾何表面取樣點雲不能直接冒充相機觀測或深度反投影測試。

## 10 完整驗證包的完成定義

完整驗證包完成時，應具備以下可執行內容，並附實際結果與版本。

1. 可重現的建置環境、固定資料集與數值介面規格。
2. 獨立參考計算及可執行的各模組測試。
3. 點雲至路徑的完整 SoC 軟體功能模型。
4. 模組間狀態、記憶體版本、容量及完成條件的整合測試。
5. 與待測模型分離的路徑驗證器及其適用保證範圍。
6. 一個總入口，可輸出逐案例 PASS 或 FAIL、第一差異與重現材料。
7. 完整回歸與成功失敗統計，沒有未解決的必要正確性失敗。
8. 若報告速度與耗電，附 functional first 模型、器件假設及能量係數來源。

軟體功能完成的核心驗收是前七項。第八項形成硬體效益評估；P9 再銜接 RTL，而不是把未完成的 RTL 當成軟體功能驗證的前置條件。

## 11 第一輪實際工作清單

第一輪先完成 P0 與 P1，接著做 P2 的量化與 Morton 編碼。此時不要求整顆 SoC 已存在。

- 核對現有資料完整性報告，選定一筆已確認有效的 Panda 問題。
- 跑通固定 commit 的 VCC baseline，保存命令、環境、輸入及結果。
- 寫出 design v1 的模組介面、位元規格與錯誤狀態。
- 建立可以讀取同一 case 的 runner，先測已知小案例。
- 寫逐位元 Morton 參考與待測量化編碼，建立邊界與故障案例。
- 輸出第一份模組比對報告，確認失敗定位有效，再接中心點濾波。

此輪完成的證據應是一套能執行且會抓錯的最小驗證流程，以及第一個符合規格的模組。
